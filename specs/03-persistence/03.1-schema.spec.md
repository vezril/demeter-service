# 03.1 — Storage Schema

## Intent

The database shape, chosen to make three things cheap: (a) replaying normalization from
archived raw responses, (b) building price history keyed on `ProductKey`, and (c) diffing
flyers week over week. PostgreSQL, not SQLite — you want concurrent writes during a fan-out
run and real time-series queries. Schema is spec'd here as behaviour/invariants; the DDL is
the implementation.

## Tables

```
raw_response
  id              bigserial pk
  source          text            -- "flipp", "pcexpress", …
  kind            text            -- "flyers" | "flyer_items" | "search"
  url             text
  postal_code     text
  locale          text
  fetched_at      timestamptz
  content_type    text
  body            bytea           -- the exact bytes (03.2)
  body_sha256     bytea           -- dedup identical fetches

merchant
  id              int pk          -- Flipp merchant_id
  name            text

flyer
  id              bigint pk       -- Flipp flyer id
  merchant_id     int fk merchant
  name            text
  valid_from      timestamptz
  valid_to        timestamptz
  postal_code     text
  locale          text
  first_seen_at   timestamptz     -- for dedup ledger (03.4)
  last_seen_at    timestamptz
  raw_response_id bigint fk       -- provenance

product
  key             text pk         -- ProductKey (02.7)
  merchant_id     int fk
  display_name_en text
  display_name_fr text
  size_qty        numeric null
  size_unit       text null
  first_seen_at   timestamptz

price_observation
  id              bigserial pk
  product_key     text fk product
  merchant_id     int fk
  flyer_id        bigint fk flyer
  observed_at     timestamptz
  effective_cents bigint null     -- null is legal (PercentOffUnknown etc.)
  price_basis     text
  original_cents  bigint null
  unit_cents      bigint null
  unit_basis      text null       -- PerLitre|PerKg|PerItem
  sale_text       text null
  valid_from      timestamptz
  valid_to        timestamptz
  confidence      text
  raw_response_id bigint fk       -- which fetch this came from
  UNIQUE (product_key, flyer_id, observed_at)   -- idempotent re-runs
```

## Invariants

- **Raw before parsed**: a `price_observation` always references the `raw_response` it was
  derived from. You can delete every observation and rebuild from `raw_response` alone.
- **Nullable prices are first-class**: `effective_cents` NULL is a valid, queryable state,
  not a sentinel like `-1` or `0`.
- **Idempotency**: re-running the same day's fetch must not create duplicate observations —
  the unique constraint makes re-runs safe (03.3 relies on upsert).
- **No flyer imagery** is stored anywhere (legal boundary). `raw_response.body` for the
  `flyer_items` kind may contain image *URLs*; that's fine (they're facts/links), but the
  images themselves are never fetched or stored.

## Gherkin

```gherkin
Feature: Schema invariants

  @boundary
  Scenario: Every observation is traceable to a raw response
    Given a stored price_observation
    When I look up its raw_response_id
    Then a raw_response row exists with those exact bytes

  @boundary
  Scenario: A null effective price is storable and queryable
    Given an observation with no effective price and basis PercentOffUnknown
    When I store it and query for promos with unknown prices
    Then the observation is returned

  @boundary
  Scenario: Re-storing the same observation is idempotent
    Given an observation already stored for (product_key, flyer_id, observed_at)
    When I store an observation with the same key triple
    Then no duplicate row is created

  @boundary
  Scenario: History can be rebuilt from raw responses alone
    Given a set of raw_response rows and an empty price_observation table
    When I replay normalization over the raw responses
    Then price_observation is repopulated
    And the rebuilt observations match the originals for clean cases
```

## Notes

- `body_sha256` lets you skip re-parsing an identical fetch and detect "Flipp returned the
  exact same bytes as yesterday" (a flyer that didn't change).
- Partition `price_observation` by month if it grows; not needed at personal scale for a
  long time, noted so the pk/uniqueness choice doesn't block it later.
- doobie is the intended access layer; keep SQL in one repository module per table so the
  boundary is thin and the queries are reviewable.
