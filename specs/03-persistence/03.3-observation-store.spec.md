# 03.3 — Observation Store

## Intent

Persist normalized `PriceObservation`s idempotently, upsert `product` rows, and expose the
read queries that 04 (watchlist), 05 (alerting), and 07 (history) need. The idempotency
here is what makes the daily job safe to re-run after a partial failure — a crash halfway
through a fan-out must not double-count prices in the history.

## Contract

```scala
trait ObservationStore[F[_]]:
  def upsertProduct(p: Product): F[Either[DealWatchError, Unit]]
  def save(obs: PriceObservation, rawId: RawResponseId): F[Either[DealWatchError, Unit]]
  def saveAll(obs: List[PriceObservation], rawId: RawResponseId): F[Either[DealWatchError, SaveReport]]
  def observationsFor(key: ProductKey, since: Instant): F[List[PriceObservation]]
  def currentObservations(merchant: MerchantId, activeAt: Instant): fs2.Stream[F, PriceObservation]

final case class SaveReport(inserted: Int, skippedDuplicate: Int, failed: Int)
```

- `save` upserts on `(product_key, flyer_id, observed_at)` — an existing triple is a no-op
  (counted as `skippedDuplicate`), never an error, never a duplicate.
- `saveAll` is transactional per flyer: either the batch's inserts commit or the batch rolls
  back, and it returns counts (feeds 08.3 metrics).
- `observationsFor` powers 07's rolling stats; `currentObservations` powers 04's matching
  against what's on sale right now.

## Gherkin

```gherkin
Feature: Idempotent observation persistence

  @boundary
  Scenario: Saving the same observation twice inserts once
    Given an observation for (key K, flyer F, time T)
    When I save it twice
    Then the save report shows 1 inserted and 1 skipped duplicate
    And the store holds exactly one matching row

  @boundary
  Scenario: A batch save reports per-item outcomes
    Given a batch of 10 observations where 2 duplicate existing rows
    When I saveAll
    Then the report shows 8 inserted and 2 skipped

  @boundary
  Scenario: Saving a product observation upserts the product dimension
    Given an observation whose product key is not yet in the product table
    When I save it
    Then a product row is created with the display names and size

  @boundary
  Scenario: History query returns observations for a key since a cutoff
    Given 3 observations for key K across 3 weeks
    When I query observations for K since 2 weeks ago
    Then exactly the 2 within the window are returned, newest-ordered

  @boundary
  Scenario: Current observations return only those active at a given time
    Given observations with various valid windows
    When I stream current observations for a merchant active now
    Then only observations whose window contains now are yielded
