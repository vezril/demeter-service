# 02.7 — Product Key

## Intent

Flipp has **no stable product identifier** across weeks (01.4: `sourceItemId` changes). To
build price history (07) you need to recognize "this week's Natrel 4L milk at Metro" as the
same product as last week's. This unit derives our *own* stable `ProductKey` from the
attributes that don't change: merchant + normalized name + size. It is the linchpin of price
history, and it is necessarily imperfect — so it also emits a confidence and never claims a
match it can't justify.

## Approach

- `ProductKey` = a hash of `(merchantId, normalizedNameTokens, size)`.
- `normalizedNameTokens` reuses 04.2's text normalizer (lowercase, accent-fold, drop
  punctuation, sort? no — keep order but drop stopwords) so `"LAIT NATREL 4 L"` and
  `"Natrel milk 4L"` at the same merchant collide **only if** they normalize alike. Cross-
  language collision is *not* attempted here (that's harder; see notes) — the key is within
  a merchant and within a language form, using the item's primary form.
- Size (02.4) is part of the key: 2L and 4L milk are different products.
- Deliberately merchant-scoped. Cross-merchant product identity (same milk at IGA and Metro)
  is a *separate, harder* problem handled fuzzily in 07, not here. Keeping this key
  merchant-scoped keeps it trustworthy.

## Contract

```scala
final case class ProductKey(value: String)   // opaque, stable hash

def productKey(merchantId: MerchantId, name: BilingualText, size: Option[Size]): ProductKey
```

- Pure and deterministic: same inputs → same key, always. This is a hard requirement — the
  entire history join depends on it.

## Gherkin

```gherkin
Feature: Stable product key derivation

  @pure
  Scenario: The same product across two weeks yields the same key
    Given merchant 123, name "Natrel Milk 4 L", size 4 litres
    And the same product next week named "NATREL MILK 4L" at merchant 123
    When I derive the product key for each
    Then the two keys are equal

  @pure
  Scenario: Accents and case do not change the key
    Given merchant 123, name "LAIT NATREL 4 L"
    And merchant 123, name "lait natrel 4 l"
    When I derive both keys
    Then they are equal

  @pure
  Scenario: Different sizes yield different keys
    Given merchant 123, name "Natrel Milk 2 L"
    And merchant 123, name "Natrel Milk 4 L"
    When I derive both keys
    Then they are different

  @pure
  Scenario: The same product at different merchants yields different keys
    Given merchant 123, name "Natrel Milk 4 L"
    And merchant 456, name "Natrel Milk 4 L"
    When I derive both keys
    Then they are different

  @pure
  Scenario: A missing size still yields a deterministic key
    Given merchant 123, name "Assorted Hand Tools", no size
    When I derive the key twice
    Then both derivations are equal

  @pure @property
  Scenario: Key derivation is a pure function
    Given any merchant id, name, and size
    When I derive the key any number of times
    Then every derivation is identical
```

## Notes

- This will both over-split (same product named two ways collides less than it should) and
  under-split (two genuinely different products normalize alike) at the margins. That is
  acceptable for v1 *because* 07 treats history as statistical, not exact: a slightly noisy
  key produces a slightly noisier median, not a crash. Don't gold-plate.
- Cross-language identity is explicitly out of scope for the key. If you want French and
  English forms of the same item to share history, that's a 07 concern using both `forms`
  from `BilingualText`, and it should be additive, not baked into this key.
- Keep the hash algorithm and the normalization version *stamped* into the key (e.g. a
  `v1:` prefix) so that when you improve normalization you can migrate history deliberately
  rather than silently orphaning it.
