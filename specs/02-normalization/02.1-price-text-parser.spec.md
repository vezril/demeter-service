# 02.1 — Price Text Parser

## Intent

Pull a clean `Money` out of a single free-text price token like `$4.99`, `4,99 $`, `99¢`,
`$1.50/lb`. This is the lowest layer of the normalization stack: multibuy (02.2) and
percentage-off (02.3) parse *structure* and then call down into this to interpret the money
tokens they find. Pure, total (returns `Option`), and a prime mutation target — the bugs
here are exactly the sneaky ones (¢ vs $, comma-decimal, trailing `/lb`).

## What it handles

- Leading or trailing currency symbol: `$4.99`, `4.99$`, `4,99 $` (Quebec French format).
- Comma as decimal separator (French): `4,99` → 499 cents. (This is why 00.1 rejects commas
  — that concern is resolved *here*, then handed clean digits to `Money`.)
- Cents notation: `99¢`, `99 cents`, `.99`.
- Unit suffixes stripped and **captured separately** (not discarded): `/lb`, `/kg`, `ea`,
  `each`, `chacun`. The suffix is returned alongside the money so 02.4 can compute unit
  price and 02.6 can record the basis.
- Rejects (returns `None`): text with no parseable money (`"see store"`, `"BOGO"`,
  `"gratuit"` handled by 02.3 not here), empty string.

## Contract

```scala
final case class PriceToken(amount: Money, unit: Option[PriceUnit])
enum PriceUnit { case PerLb, case PerKg, case Each, case Per100g /* … */ }

def parsePriceToken(text: String, locale: Locale): Option[PriceToken]
```

- Locale hints comma-vs-dot preference but the parser is tolerant of both regardless, because
  Quebec flyers mix them.

## Notes

- Thousands separators: `1 234,05` (French uses a thin/regular space) and `1,234.05`
  (English). Strip grouping *before* interpreting the decimal mark. This ordering is the
  bug-prone part; test both directions.
- The parser captures `unit` rather than dropping it because a `$1.50/lb` deal and a
  `$1.50 each` deal are wildly different value propositions, and 07's "good deal?" logic must
  not compare across bases. Provenance again.
