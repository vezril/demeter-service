# 08.3 — Observability

## Intent

Make the service's health legible, because an undocumented-endpoint scraper fails *silently*
by default: Flipp changes a field, decode-failure rate quietly climbs, and you notice weeks
later that alerts stopped. This unit defines the metrics, the drift alarms, and the run
report that turn silent decay into a visible signal — plus an optional read-only status
endpoint for your own dashboard.

## What it exposes

- **RunReport** per run: flyers listed / selected / fetched / failed, items parsed / dropped,
  observations inserted / skipped, matches, alerts delivered / suppressed **broken down by
  05.1's suppression reason**, sources degraded, wall-clock.

  The breakdown was added 2026-08-20 after a real run reported "398 matches, 0 alerts, 398
  suppressed" — technically complete and diagnostically useless. Silence has several very
  different causes, and a bare total cannot tell them apart: a price ceiling set too tight,
  an empty price history, or simply having already told you. The same run with reasons
  attached read "224 above max price, 160 not a sale, 14 price unknown", which says
  immediately which knob to turn. 05.1 always carried the reason for this purpose; it was
  being discarded here.
- **Drift alarms** (the important part):
  - decode-failure rate per source above a threshold → alarm (Flipp schema drift).
  - zero-result anomaly: a source that normally returns N flyers/items returns ~0 → alarm
    (silent breakage, distinct from a genuine empty search per 01.3).
  - alert-volume anomaly: sudden drop to zero alerts across a normally-active watchlist.
- **Metrics** emitted in a scrape-friendly form (Prometheus text or structured logs) so HA or
  a small dashboard can chart them.
- **Optional read-only HTTP** `/status` and `/history/{productKey}` for personal use (README
  allows a self-consumption read API; no flyer content redistribution).

## Gherkin

```gherkin
Feature: Observability and drift detection

  @boundary
  Scenario: A run emits a complete report
    Given a completed run
    When I read the run report
    Then it includes counts for flyers, items, observations, matches, and alerts
    And it lists any degraded sources

  @boundary
  Scenario: A decode-failure spike raises a drift alarm
    Given a source whose decode-failure rate exceeds the configured threshold
    When the run finishes
    Then a drift alarm is raised naming the source
    And the alarm distinguishes decode drift from a transport outage

  @boundary
  Scenario: A zero-result anomaly is flagged, distinct from a genuine empty search
    Given a source that historically returns many flyers
    When a run gets zero flyers from it with no transport error
    Then a zero-result anomaly is raised
    And a genuinely empty item search does not raise one

  @boundary
  Scenario: The status endpoint serves own-consumption data only
    Given the read-only status endpoint is enabled
    When I query it
    Then it returns run health and price history
    And it does not serve raw flyer imagery or bulk flyer content
