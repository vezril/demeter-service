# 08.4 — Configuration

## Intent

Lift every operational knob out of code into one validated config, loaded at startup and
failing fast on bad input. This is where the single postal code lives (so multi-postal is a
config change, not a rewrite), where API keys are injected (never hardcoded — 06.2), where
rate limits and scoring weights are tuned, and where sinks are wired. A misconfiguration
should stop the service at boot with a clear message, not surface as a mystery three layers
deep at 3 a.m.

## Shape

```scala
final case class Config(
  postalCode: PostalCode,               // v1 single; List for future multi
  locale: Locale,
  sources: SourceConfig,                // Flipp base URL, fallback (Apify) token, toggles
  enrichment: EnrichmentConfig,         // per-source keys/toggles (PC Express X-Apikey, …)
  http: HttpPolicyConfig,               // timeout, attempts, backoff, rate limits, UA
  scoring: ScoringConfig,               // match weights (04.4), deal thresholds (07.3)
  history: HistoryConfig,               // window length, min-n floors (07.2/07.3)
  sinks: SinkConfig,                    // HA webhook/MQTT, ntfy, telegram, email, order
  schedule: ScheduleConfig,             // cron/interval for the daily run
  storage: StorageConfig                // Postgres connection
)
```

## Contract

- Loaded once at startup, fully validated; **invalid config fails fast** with a specific
  message (bad postal code, missing required key for an enabled source, empty sink chain).
- **Secrets** (API keys, DB password, sink tokens) come from environment / secret file, never
  from a committed file and never logged. A config dump redacts them.
- Every default that appears in a spec (backoff base/cap, mutation-relevant weights, history
  window) has its home here, so tuning is a config edit with no recompile.
- Enabling a source you haven't supplied a key for is a boot-time error, not a silent
  runtime degradation.

## Gherkin

```gherkin
Feature: Validated fail-fast configuration

  @boundary
  Scenario: An invalid postal code stops startup
    Given a config with postal code "12345"
    When the service loads config
    Then startup fails with a clear postal-code error

  @boundary
  Scenario: Enabling a source without its key fails at boot
    Given PC Express enrichment is enabled
    And no PC Express API key is provided
    When the service loads config
    Then startup fails naming the missing key
    And the service does not start in a half-configured state

  @boundary
  Scenario: An empty sink chain is rejected
    Given a config whose alert sink chain is empty
    When the service loads config
    Then startup fails
    Because alerts would have nowhere to go

  @boundary
  Scenario: A config dump redacts secrets
    Given a loaded config with API keys and a DB password
    When the config is logged at startup
    Then secret values are redacted
    And non-secret settings are shown for diagnostics

  @pure
  Scenario: The single postal code is the only place location is set
    Given the v1 config
    Then the postal code appears once
    And adding more postal codes later is an additive config change
