# 01.6 — HTTP Client Policy

## Intent

One place that owns *how* we talk to undocumented endpoints politely and defensibly: retry,
backoff, timeout, jitter, headers, and the bot-wall detection that feeds 00.5. Shared by all
boundary adapters (01 and 06) so the "be a good citizen" rules are defined once and can't
drift per-source. This is also the unit that keeps you on the low-risk side of the legal
line (README): low volume, realistic pacing, no hammering.

## Contract

- **Timeout**: per-request connect + read timeout (config, default 30s). A timeout →
  `Timeout` error (retriable).
- **Retry**: retriable errors (00.5 table) retried with **exponential backoff + full
  jitter**, capped attempts (default 3) and a max total wait. Non-retriable errors are not
  retried.
- **Rate limiting**: a token-bucket limiter shared across a source so the daily run can't
  accidentally burst. Default: a few requests/minute per source, config in 08.4.
- **Headers**: a realistic, stable `User-Agent` and `Accept-Language` matching the requested
  locale. No spoofing of auth. Header set is config-visible, not hidden.
- **Bot-wall detection**: a 403, a 429 with a challenge marker, or a body matching known
  challenge signatures (Cloudflare `cf-chl`, captcha markers) → `BotWall`, which is
  non-retriable and escalates (00.5).
- **Idempotency**: all calls are GETs; retries are always safe. This is stated so no one
  later adds a non-idempotent call behind this policy.

## Backoff, pinned

```
attempt n wait = min(cap, base * 2^(n-1)) * random_in[0,1]     # full jitter
base default = 1s, cap default = 30s, maxAttempts default = 3
```

## Gherkin

```gherkin
Feature: Polite, resilient HTTP policy

  @boundary
  Scenario: A retriable error is retried up to the attempt cap then surfaced
    Given a transport that fails with 503 on every attempt
    And a max attempt count of 3
    When I make a request through the policy
    Then exactly 3 attempts are made
    And the final result is Left(HttpStatus(503))

  @boundary
  Scenario: A non-retriable error is not retried
    Given a transport that returns 404
    When I make a request through the policy
    Then exactly 1 attempt is made
    And the result is Left(HttpStatus(404))

  @boundary
  Scenario: A success on the second attempt returns without further tries
    Given a transport that fails once with a timeout then succeeds
    When I make a request through the policy
    Then 2 attempts are made
    And the result is a Right

  @pure @property
  Scenario Outline: Backoff wait stays within the jittered bound
    Given base 1s, cap 30s
    When I compute the wait for attempt <n>
    Then the wait is between 0 and min(30s, 1s * 2^(<n>-1))

    Examples:
      | n |
      | 1 |
      | 2 |
      | 5 |
      | 8 |

  @boundary
  Scenario: A Cloudflare challenge short-circuits to BotWall without retry
    Given a transport returning 403 with body marker "cf-chl-bypass"
    When I make a request through the policy
    Then the result is Left(BotWall)
    And exactly 1 attempt is made

  @boundary
  Scenario: The rate limiter serializes bursts within a source
    Given a limiter of 2 requests per second
    When I issue 5 requests in a tight loop
    Then the requests are spaced so no more than 2 start within any 1-second window

  @boundary
  Scenario: Accept-Language matches the requested locale
    Given a request for locale fr-ca
    When the policy builds the headers
    Then the Accept-Language header prefers French
```

## Notes

- Full jitter (not "equal jitter" or fixed backoff) is chosen deliberately to avoid a
  thundering-herd against a single small backend when multiple flyers are fetched in a run.
- The bot-wall body markers live in a config list so you can add signatures without a
  redeploy when Flipp's challenge page changes.
- This unit is `@boundary` heavy but the backoff math is `@pure` — split the timing
  calculation into a pure function so it can be property-tested without a clock.
