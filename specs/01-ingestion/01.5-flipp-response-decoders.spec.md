# 01.5 — Flipp Response Decoders

## Intent

The pure functions that turn Flipp's JSON into domain objects. Separated from the boundary
adapters (01.2–01.4) so they can be tested exhaustively against fixtures with zero network,
and so they're the mutation-testing focus. Every "Flipp changed a field" surprise lands
here first. These decoders are lenient in a *disciplined* way: they tolerate the messiness
the endpoints actually exhibit (null prices, mixed types, extra fields) while rejecting data
that would corrupt the domain (bad time windows, non-numeric prices that aren't null).

## Contract

- Written as circe `Decoder`s but the *behaviour* below is what's specified, not the library.
- **Unknown fields are ignored**, never fatal. Flipp adds fields regularly.
- A price field may be a JSON number, a numeric string, or `null`. Number/​numeric-string →
  `Some(Money)`; `null`/absent → `None`; a non-numeric non-null string → `Decode` error for
  *that field*, which the item-level policy (01.4) turns into a drop-and-count.
- Timestamps parse as ISO-8601 with offset → `Instant`. A window with `validTo <= validFrom`
  is a `Decode` rejection of that item.
- Decoders emit `DealWatchError.Decode(source, pointer, reason)` with a JSON pointer to the
  offending path, so a drift shows up in logs as `items[3].current_price` not "parse error".

## Units within this spec

1. `priceField` decoder — number | numeric-string | null → `Option[Money]`
2. `instantField` decoder — offset datetime → `Instant`
3. `flyerDecoder` — one flyer object → `Flyer`
4. `flyerItemDecoder` — one item object → `FlyerItem`
5. `listingDecoder` / `itemsDecoder` / `searchDecoder` — top-level envelopes

## Gherkin

```gherkin
Feature: Price field decoding tolerates Flipp's real shapes

  @pure
  Scenario Outline: A price field decodes across the shapes Flipp actually sends
    Given the JSON price field value <json>
    When I decode it as an optional Money
    Then the result is <result>

    Examples:
      | json    | result        |
      | 4.99    | Some(499)     |
      | "4.99"  | Some(499)     |
      | 10      | Some(1000)    |
      | null    | None          |
      | (absent)| None          |
      | 0       | Some(0)       |

  @pure
  Scenario Outline: A non-numeric non-null price is a field-level decode error
    Given the JSON price field value <json>
    When I decode it as an optional Money
    Then it fails with a Decode error naming the field

    Examples:
      | json      |
      | "N/A"     |
      | "see store" |
      | "$4.99"   |   # currency symbol is not this decoder's job; upstream sends bare numbers here

Feature: Instant decoding

  @pure
  Scenario Outline: Offset datetimes parse to instants
    Given the timestamp "<ts>"
    When I decode it as an Instant
    Then it succeeds

    Examples:
      | ts                          |
      | 2026-07-23T04:00:00+00:00   |
      | 2026-07-30T03:59:59+00:00   |
      | 2026-07-23T04:00:00Z        |

  @pure
  Scenario: A malformed timestamp is a decode error
    Given the timestamp "not-a-date"
    When I decode it as an Instant
    Then it fails with a Decode error

Feature: Item decoding invariants

  @pure @contract
  Scenario: A real captured item decodes to the expected FlyerItem
    Given the first item in "fixtures/items_search.sample.json"
    When I decode it
    Then it yields a FlyerItem with a non-empty rawName
    And its price fields match the fixture

  @pure
  Scenario: An item with validTo before validFrom is rejected
    Given an item with valid_from after valid_to
    When I decode it
    Then it fails with a Decode error

  @pure
  Scenario: Unknown extra fields do not break decoding
    Given a flyer item JSON containing three fields this decoder has never seen
    When I decode it
    Then it decodes successfully
    And the unknown fields are ignored
```

## Notes

- The `"$4.99"` example failing here is intentional and coordinated with 00.1: the raw
  endpoints send bare numeric prices in the price *fields*; dollar signs only appear inside
  `sale_story`/`name` free text, which 02 handles. If a future source puts `$` in a price
  field, add a tolerant variant rather than loosening this one.
- Property angle: generate arbitrary objects with random extra keys and assert decode still
  succeeds — cheap protection against the "additive schema change breaks us" failure.
