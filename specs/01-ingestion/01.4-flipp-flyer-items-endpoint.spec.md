# 01.4 — Flipp `flyers/{id}` Items Endpoint Adapter

## Intent

Adapt "give me every item in this specific flyer". This is the backbone of the daily run:
once 03.4 identifies a new/changed flyer, this pulls its full item set for normalization
and storage. It's also where Flipp's data is *worst* — big-box flyers return hundreds of
items with null prices and everything encoded in free text — so the adapter must be
tolerant and hand the mess to 02 rather than choking on it.

## Endpoint (verified live 2026-07-26)

```
GET https://backflipp.wishabi.com/flipp/flyers/{flyer_id}
      ?locale={en-ca|fr-ca}
      &postal_code={CANONICAL}
```

Verified behaviour: for a Canadian Tire flyer this returned a top-level `items` array of
**776 items**, plus `pages` and `has_corrections`. Critically, most Canadian Tire items had
`current_price: null` and `original_price: null`, with the actual offer living in the `name`
string and/or `sale_story`. A Metro grocery flyer, by contrast, returned clean scalar
`current_price` values.

### CORRECTION (verified live 2026-08-20)

The table below describes the **items/search** shape, not this endpoint's. A real
`GET /flipp/flyers/{id}` item carries:

```
id, flyer_id, name, short_name, brand, price (a STRING), discount (an INT),
display_type, text_areas, valid_from, valid_to, available_to, print_id, ...
```

There is **no `merchant_id`**, **no `current_price`**, **no `sale_story`**, and
**no `flyer_item_id`**. Merchant identity genuinely does come from the flyer, as
this spec's Contract section already said — the field table just contradicted it.
`discount` is an integer of undocumented units; it is preserved as opaque sale
text rather than read as a percentage, because fabricating an original price
from a guess would corrupt discount gating (05.1) and verdicts (07.3).

`fixtures/flyer_items.sample.json` is a real capture of this endpoint.

### Fields we consume (SEE CORRECTION ABOVE — this table is the search shape)

| JSON field | Domain | Notes |
|---|---|---|
| `flyer_item_id` / `item_id` | `sourceItemId` | unstable across weeks |
| `name` | `rawName` + `BilingualText` | may be `"FR | EN"` bilingual (02.5) |
| `current_price` | `currentPrice` | **frequently null** — expected, not an error |
| `original_price` | `originalPrice` | often null |
| `sale_story` | `saleStory` | e.g. `"2 for $5"`, `"25 points"`, `"50% off"` |
| `pre_price_text` / `post_price_text` | fold into `saleText` | e.g. "from", "/lb" |
| `valid_from` / `valid_to` | window | |
| `merchant_id` | `MerchantId` | **`merchant_name` often null here** — join needed |

## Contract

- A null `current_price` is **never** a decode failure. It produces a `FlyerItem` with
  `currentPrice = None`; deriving a usable price from `name`/`sale_story` is 02's job.
- `merchant_name` being null here is expected. The adapter fills merchant identity from the
  `flyerId → merchantId → Merchant` mapping the orchestrator already has from 01.2, and if
  it can't, leaves `merchantId` and lets 03 resolve the name on read.
- Malformed *individual* items (missing `name`, `valid_from > valid_to`) are dropped and
  **counted**, not fatal. A per-flyer decode returns the items it could build plus a count
  of items it couldn't — that count feeds the drift alarm (08.3).
- `pages` (the flyer image pages) is ignored — that's flyer *imagery*, which we deliberately
  don't store or serve (legal boundary, README non-goals).

## Gherkin

```gherkin
Feature: Flipp per-flyer items adapter

  @boundary
  Scenario: Null current_price yields a price-absent item, not a failure
    Given a flyer item whose current_price is null and sale_story is "50% off"
    When the adapter parses it
    Then it produces a FlyerItem with no current price
    And the sale story "50% off" is preserved
    And no error is raised for that item

  @boundary
  Scenario: A grocery flyer with scalar prices decodes cleanly
    Given a flyer item with current_price 4.99
    When the adapter parses it
    Then the FlyerItem current price is 4.99

  @boundary
  Scenario: Individual malformed items are dropped and counted, not fatal
    Given a flyer response of 10 items where 2 lack a name
    When the adapter parses it
    Then it returns 8 valid items
    And it reports 2 dropped items
    And the overall result is a Right

  @boundary
  Scenario: A bilingual name is preserved raw for later splitting
    Given a flyer item named "LAIT FINEMENT FILTRÉ NATREL | NATREL FINE-FILTERED MILK"
    When the adapter parses it
    Then the FlyerItem rawName equals that exact string
    And the bilingual split is deferred to normalization

  @boundary
  Scenario: Flyer image pages are not retained
    Given a flyer response containing a pages array
    When the adapter parses it
    Then no page imagery is included in the returned items
```

## Notes

- The "drop and count" policy is the crux. 776 items where 3 are malformed should give you
  773 good observations and a `dropped=3` metric — never an exception that loses the flyer.
- This adapter is the reason 02 exists as a separate context. Resist the temptation to parse
  prices here; keep this a faithful transcription of the JSON into `FlyerItem`, warts and
  all, and let the pure normalizers earn their mutation score on the mess.
