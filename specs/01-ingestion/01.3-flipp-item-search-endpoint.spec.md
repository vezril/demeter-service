# 01.3 — Flipp `items/search` Endpoint Adapter

## Intent

Adapt Flipp's cross-merchant item search. Useful for two things: an ad-hoc "is X on sale
anywhere right now" query, and a secondary discovery path for watch terms that don't map
cleanly to a single merchant's flyer. The daily run leans mostly on `flyers` + per-flyer
`items` (01.2/01.4); search is the complement, not the backbone.

## Endpoint (verified live 2026-07-26)

```
GET https://backflipp.wishabi.com/flipp/items/search
      ?locale={en-ca|fr-ca}
      &postal_code={CANONICAL}
      &q={TERM}
```

The response has **two distinct item arrays with different meaning** — this is the single
biggest footgun in the whole Flipp integration:

- `items` — **paper-flyer** items. This is the deal data you want. For `q=milk` this
  returned 39 items. Fields (verified): `flyer_item_id`, `item_id`/`id`, `name`,
  `current_price`, `original_price`, `pre_price_text`, `post_price_text`, `sale_story`,
  `flyer_id`, `merchant_id`, `merchant_name`, `valid_from`, `valid_to`, plus bounding box
  (`top`/`left`/`right`/`bottom`) and image URLs.
- `ecom_items` — **e-commerce** listings (Walmart-style). Different shape, different
  meaning, returned 144 for `q=milk`. Has `merchant`, `description`, `average_rating`,
  `global_id`. **Do not merge these with `items` naively.**

Other top-level keys observed: `ads`, `coupons`, `coupons_v2`, `facets`, `flyers`,
`merchants`, `native_ads`, `normalized_query`, `related_flyers`, `related_items`, `sort`,
`outside_fsa_flyers`.

## Contract

- Returns `RawSearchResult` with `flyerItems` (from `items`) and `ecomItems` (from
  `ecom_items`) kept **separate**. Downstream chooses; the adapter never conflates.
- In the search response, `items[].merchant_name` **is** usually populated (unlike the
  per-flyer endpoint). Prefer it; fall back to a `merchant_id` join if absent.
- `normalized_query` is captured into the raw and surfaced, because it tells you how Flipp
  interpreted the term (useful when a watch term returns nothing).

## Gherkin

```gherkin
Feature: Flipp item search adapter

  @boundary @contract
  Scenario: The two item arrays are decoded separately
    Given the captured search response "fixtures/items_search.sample.json"
    When the adapter parses it
    Then the flyer items and the ecom items are returned as separate collections
    And no ecom item appears among the flyer items

  @boundary
  Scenario: Flyer items from search carry a usable merchant name
    Given a search response whose items include a populated merchant_name
    When the adapter parses it
    Then each flyer item's merchant is resolved from merchant_name

  @pure
  Scenario Outline: The search URL encodes the term safely
    Given the search term "<term>"
    When the adapter builds the search request
    Then the q parameter is percent-encoded as "<encoded>"

    Examples:
      | term          | encoded          |
      | milk          | milk             |
      | ground beef   | ground%20beef    |
      | café          | caf%C3%A9        |

  @boundary
  Scenario: An empty result set is a success, not an error
    Given a search for a term with no matches
    When the adapter fetches
    Then the result is a Right with zero flyer items
    And the normalized query is preserved for diagnostics
```

## Notes

- The empty-result-is-success distinction matters for 08.3: "search returned zero" is a
  *data* signal (maybe genuinely nothing on sale), whereas "search returned an error" is an
  *infrastructure* signal. Conflating them would either spam false alarms or hide real
  breakage.
- `facets` includes merchant/category counts; ignored for v1 but noted as a future filter.
