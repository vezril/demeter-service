# 06.0 — Endpoint Verification (live, 2026-08-20)

Specs 06.2–06.4 were written from public reverse-engineering and each carried the
caveat **"not executed live in this research."** This is the record of actually
looking. The short version: **all three assumed schemas are wrong**, and two of
the three sites run active bot management.

This is the intended outcome of task 9.2 — the `@contract` tests exist precisely
to confirm or deny these shapes, and the denial arrived before anything was built
on top of them.

## PC Express / Maxi — 06.2

**Assumed:** `POST https://api.pcexpress.ca/product-facade/v3/products/search`
with `Site-Banner` and a static `X-Apikey`.

**Observed:** loading maxi.ca and searching produced **no request to
`api.pcexpress.ca` at all**. Search results are server-rendered. The site also
runs **Akamai Bot Manager** — `POST /akam/13/pixel_*` plus obfuscated sensor
endpoints returning 201, fingerprinting the browser continuously.

**Status: not pursued.** Obtaining the key would mean working around controls the
operator is deliberately running. Left behind its config flag, permanently
unverified. The adapter already degrades cleanly on 401 (06.2), so nothing else
has to change.

## Voilà — 06.3

**Assumed:** `GET https://voila.ca/api/v5/products/search?term=&limit=&offset=&sort=`
gated on a `VISITORID` / `global_sid` session cookie.

**Observed:** no bot-management traffic. Clean same-origin JSON APIs, but at
entirely different paths:

```
GET /api/search/v1/suggestions/refined?searchTerm=lait&limit=20&regionId={uuid}
GET /api/search/v1/suggestions/follow-on?searchTerm=lait&limit=20&regionId={uuid}
GET /api/webproductpagews/v5/product-pages?decoratedOnly=true&limit=27&tag=web
GET /api/search/v1/redirects/active?regionId={uuid}
```

Corrections to the spec's assumptions:

- Location is a **`regionId` UUID**, not a postal code. Something has to map one
  to the other.
- No explicit session-establishment step was needed; the cookie arrives with the
  initial page load. The "establish session, retry once on 401" design in 06.3
  may be solving a problem that does not exist.
- **The priced product list is server-rendered, not returned by a JSON endpoint.**
  The `suggestions/*` endpoints return search terms, not prices.

**The data itself is excellent** — better than the spec hoped. A search for
"lait" renders name, size, price, *and a unit price*:

```
Natrel 2% Milk Partly Skimmed 2 L — 2L — ($0.28 per 100ml) — $5.69
Québon 2% Milk 2 L              — 2L — ($0.23 per 100ml) — $4.60
```

That unit price is exactly what 07.3 wants for cross-size comparison.

**Implication:** a Voilà adapter would be an **HTML scraper**, not the JSON client
`VoilaSource` currently is. That is a materially different, more fragile thing
than 06.3 specifies, and it is a rewrite rather than a fixture capture.

## Canadian Tire — 06.4

**Assumed:** a `PriceAvailability` path returning a `skus` array.

**Observed:** a real, credential-free JSON API —

```
GET /api/v1/search/v2/search?q=socket%20set&store=457   → 200
GET /api/v1/store/store/457?lang=en_CA                  → 200
```

The response envelope is nothing like the spec's guess:

```json
{ "breadcrumbList": [], "resultCount": 272,
  "sortBy": [...], "facets": [...], "inStockAtMyStore": {...} }
```

Store is an integer `store=457`, not a postal code. No API key of any kind.

**But the site also runs Akamai Bot Manager** (`POST /akam/13/pixel_2313d6ab`
plus obfuscated sensor endpoints). There is no credential to extract here — the
question is not access, it is whether to point an automated poller at a site
running bot detection. That is an operator decision, not a technical one.

## What this means for the design

`CanadianTireSource.decode` and `VoilaSource.decode` are written against
schemas that do not exist. They compile, and their stub tests pass, which makes
them look finished — they are not. Until an adapter is rebuilt against the real
shapes above, **enrichment must stay disabled in a real run.**

Worth weighing before investing further: enrichment's only job is supplying a
regular-price baseline to sharpen the deal verdict. After ~8 weeks of
first-party Flipp history, `RollingStats` produces a *better* baseline than a
retailer's claimed "regular" — that is the entire premise of the false-sale
detector in 07.3. Enrichment is most useful in the first two months of a
deployment and hardest to obtain defensibly.
